# Redis 利用回数制限 技術検証（issue #8）

## 目的・背景

Redisはスクール MUST要件（キャッシュサーバー）への対応候補であり、無料・有料プランの相談回数制限に利用する案がある。
相談本文を保存せず、ユーザーごとの回数だけを安全に数えられるかを確認する。

## 対象範囲

- 匿名のテストユーザーID単位で回数を加算する
- 上限到達前・到達時・超過時の判定を確認する
- 有効期限またはリセット方法の候補を記録する
- Redisへ保存するキー・値を定義する
- 会話本文や自由記述を保存しないことを確認する

## やらないこと

- 本番プラン価格・上限回数の決定
- 決済との完全な結合
- 会話セッション本文のRedis保存

## 検証環境

- Redis: Docker Compose で起動（`redis:7-alpine`、ホスト側ポート `6380`）
  - `technical-verification/redis-usage-limit/docker-compose.yml` を使用
  - 永続化なし（`--appendonly no`）。検証用の使い捨て環境
- クライアント: Python + `redis` パッケージ（`requirements.txt` に `redis>=5.0,<6.0` を指定）
- 実行環境: Python仮想環境（`.venv`）上で実行。OSはWindows、シェルはPowerShell
- 起動・接続確認コマンド:

  \`\`\`powershell
  docker compose up -d
  python verify_rate_limit.py
  \`\`\`

## Redisキー設計

- キー形式: `usage_limit:{user_id}`
  - `user_id` は匿名のテストユーザーID（例: `test-user-1`）を使う。実在の個人情報は含めない。
- 値: 整数（相談を開始した回数）。Redisの `INCR` コマンドでカウントする。
- 有効期限（TTL）: 初回加算時（値が1になったとき）に `EXPIRE` を設定する。
  - この検証では動作確認のため短いTTL（60秒）を使う。本番相当の期間（例: 1ヶ月）は別途検討する（Step 6で候補比較）。
- 上限判定の考え方:
  - `count < limit` → 上限到達前（許可）
  - `count == limit` → 上限到達（この回は許可。issue注意事項の「開始済みの1回は完了まで進める」方針に対応）
  - `count > limit` → 超過（拒否すべき状態）

### 採用時の注意点：INCRとEXPIREの原子性

初期実装では `INCR` と `EXPIRE` を別々のコマンドとして実行しており、その間にコネクション切断やプロセスクラッシュが発生すると、カウントだけが加算されTTLが設定されないキーが残るリスクがあった（PRレビューでの指摘により判明）。

対応として、`INCR`と初回加算時のみの`EXPIRE`を1つのLuaスクリプトにまとめ、Redis側で原子的に実行するよう修正した。Redisはシングルスレッドでスクリプトを実行するため、スクリプト内の複数コマンドの間に他の処理が割り込むことはなく、この不整合は発生しなくなる。

修正後も、単一ユーザー・複数ユーザー・障害時フェイルオープンいずれのテストも修正前と同じ結果になることを確認済み（動作を変えずに整合性のみ改善した）。

本番実装でも、カウント加算とTTL設定は同様にLuaスクリプトなどでまとめることを推奨する。

## 保存しないもの（禁止事項）

- 相談の会話全文・入力原文
- 個人情報（氏名・連絡先など）
- 実際の相談内容（テストデータは架空のものを使用する）

Redisに保存するのは「回数（整数値）」のみとし、上記は一切保存しない。

### 検証結果（Redisに保存されている内容の実データ確認）

検証中、Redis DB内の全キーを確認したところ、`usage_limit:test-user-1` / `usage_limit:test-user-2` の2件のみで、値はいずれも整数（`type=string`、中身は`"3"`のような数値のみ）だった。会話内容・入力原文・個人情報に該当するデータは一切存在しないことを確認した。

['usage_limit:test-user-1', 'usage_limit:test-user-2']
usage_limit:test-user-1 = 3  type= string
usage_limit:test-user-2 = 3  type= string
\`\`\`

## 検証結果

### 加算・上限判定（単一ユーザー）

上限を3（検証用の仮値）として `test-user-1` に対して5回加算した結果：

| 実行回 | count | 判定結果 |
| --- | --- | --- |
| 1回目 | 1 | before_limit（上限到達前） |
| 2回目 | 2 | before_limit（上限到達前） |
| 3回目 | 3 | limit_reached（上限到達・この回は許可） |
| 4回目 | 4 | over_limit（超過） |
| 5回目 | 5 | over_limit（超過） |

TTLは想定通り60秒で設定されることを確認した（`EXPIRE` は初回加算時のみ実行）。

→ 上限到達前・到達時・超過時の判定は想定通り動作することを確認できた。

### 複数ユーザーの分離

`test-user-1` と `test-user-2` を交互に3回ずつ加算した結果、両者とも `count=3` となり、片方の加算がもう片方に混ざることはなかった。Redis上のキーも `usage_limit:test-user-1` / `usage_limit:test-user-2` として別々に保存されていることを確認した。

→ ユーザーごとの回数は独立してカウントできることを確認できた。

## リセット方式の候補（比較）

| 候補 | 概要 | メリット | デメリット |
| --- | --- | --- | --- |
| ① TTL方式（本検証で採用・実装済み） | 初回加算時に`EXPIRE`でキーの有効期限を設定する。期限が切れると自動的にキーが消え、次回加算時にcount=1から再開する。 | 実装がシンプル。Redis自体が期限切れを処理するため、リセット用のバッチ処理やスケジューラが不要。 | リセットのタイミングがユーザーごとの「初回利用時刻」基準になる（全員が同じ日にリセットされるわけではない）。 |
| ② 日付キー方式 | キーに期間を含める（例: `usage_limit:{user_id}:{yyyy-mm}`）。期間が変わると別キーになるため、自然に0から数え直せる。 | 「毎月1日に全員リセット」のような、カレンダー基準の要件に対応しやすい。 | キー名の設計・タイムゾーンの扱いが①より複雑になる。古い期間のキーを消すには、結局TTL設定か別途削除処理が必要。 |
| ③ バッチリセット方式 | キーに期間を含めず、定期実行するバッチ処理（cronなど）が一括で`DEL`または`SET 0`する。 | リセットタイミングを完全に制御できる。 | バッチ処理という追加のインフラ・スケジューラが必要。バッチが失敗すると誰もリセットされないまま放置されるリスクがある。 |

### この検証での結論

- 本検証では**候補①（TTL方式）**を採用し、動作を確認した（Step 4・5参照）。
- 理由: 追加のバッチ処理やスケジューラが不要で、Redis単体で完結するため、MVPの実装コストが低い。
- ただし、プラン仕様（無料/有料の切り替えタイミング、全員同じ日にリセットしたいか等）が確定していないため、「①で確定」ではなく「①を第一候補とし、カレンダー基準のリセットが必須要件になった場合は②を再検討する」という記録にとどめる。
- 候補③は、障害時にリセットされないリスクがあるため、この検証時点では非推奨とする。

### 未確認事項

- 実際に採用する期間（1日／1ヶ月など）はプラン仕様が未確定のため、この検証では仮の60秒で代用した。本番の期間は別途決定が必要。
- Redis再起動時にデータが失われた場合（`--appendonly no`のため）の扱いは、この技術検証では未確認（本検証用コンテナは永続化なしの設定のため想定内だが、本番用Redisの永続化方針は別途検討が必要）。

## 障害時の方針

Redisへの接続・コマンド実行でエラーが発生した場合、相談中のユーザーを止めないことを優先し、**フェイルオープン（判定不能時は許可扱い）**とする。

- 理由: 完了条件、および企画案の「無料でも開始済みの1回は相談完了まで進める」という方針に基づき、インフラ障害を理由にユーザーの相談を止めることは避ける。
- 実装方針: Redis呼び出しは例外処理でラップし、`RedisError`（接続失敗・タイムアウト等）が発生した場合は、回数判定をスキップして「許可」扱いとする。あわせてエラーをログに記録し、監視・アラートの対象とする（無制限の使い放題を放置しないため）。
- 適用範囲: 相談を開始する時点の判定、相談途中の判定のどちらでも同じ方針を適用する。

### 検証結果

Redisコンテナを停止した状態で `verify_redis_failure.py` を実行し、例外で処理が落ちずに許可扱いとして継続することを確認した。

\`\`\`text
WARNING:usage_limit:Redisエラーのため回数判定をスキップし、通過扱いにする: Timeout connecting to server
count=None, status=redis_unavailable_allowed
\`\`\`

その後Redisコンテナを再起動し、`verify_rate_limit.py` を再実行したところ、通常時の判定（加算・上限判定・TTL・複数ユーザー分離）が問題なく動作することを確認した（Step4・5と同じ結果）。

（参照: `technical-verification/redis-usage-limit/verify_redis_failure.py`）

### 未確認事項・今後の検討

- フェイルオープンを無制限に許容すると、Redis障害中は回数制限が事実上無効になる。障害が長時間続いた場合の運用対応（アラート後にどう扱うか）は本検証の範囲外とし、後続Issue・運用フェーズで検討する。
- 本番のRedis接続タイムアウト値は、この検証で使用した2秒を含め未確定。

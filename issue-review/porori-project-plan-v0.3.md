## 1. 企画概要

ぽろり。は、パートナーとの関係を大切にするあまり、不満や本音を自分の中だけで処理してしまう人が、AIとの段階的な対話で気持ちを整理し、その気持ちを「伝える・今は保留する・伝えない」のどれで扱うかを自分で選ぶためのWebアプリです。

- **開発体制**：5人チーム
- **位置づけ**：スクールの最終プロジェクト
- **提供形態**：スマートフォンでの利用を中心に想定したWebアプリ

## 2. 背景と解決したい課題

関係を大切にする人ほど、「不満は自分で消化すべき」と考え、自分の気持ちを後回しにすることがあります。一人で処理し続けると、出来事・感情・本音・望みが混ざり、自分が何を感じ、どうしたいのか分からなくなることがあります。

家族や友人には評価や人間関係があって話しづらく、パートナー本人にもまだ話せないとき、利害関係から離れて気持ちを整理できる「第三の場所」が必要だと考えました。

### 解決したい課題

> パートナーとの関係を大切にするあまり、不満や違和感を自分の中だけで処理し続け、自分の感情・本音・望みが分からず、その気持ちをどう扱うか決められない。

厚生労働省の「今の気持ちを書いてみる」では、気持ちを書き出すことが、悩みと距離を取り、落ち着いて考え、新しい選択肢に気づくことにつながると紹介されています。一方、AIアプリとしての有効性は資料だけでは証明できないため、ヒアリングと画面試用で確認します。

参考：[厚生労働省「今の気持ちを書いてみる」](https://www.mhlw.go.jp/kokoro/youth/self/text2.html)

## 3. 想定ユーザー

主なペルソナは、パートナーがいる20〜30代のうち、関係を大切にしているからこそ不満や本音を抱え込んでしまう人です。

- 嫌われることや関係悪化が怖く、本音を言いづらい
- 相手を尊重するあまり「自分で解決すべき」と考える
- 自分の気持ちを後回しにし、何を感じているか分からなくなる
- 気持ちは分かっても、どう扱うか決められない

20〜30代という設定は、初期の調査・画面試用の対象を具体化するための仮置きです。サービス利用を年齢で制限するものではなく、性格や診断名ではなく困りごとと状況で対象を捉えます。

## 4. プロダクトゴール

> 自分の感情と本当の望みを言葉にし、その気持ちを「伝える・今は保留する・伝えない」のどれで扱うかを自分で選べるところまで整理できること。

### 1回の利用で目指す状態

> 私はこの出来事で「○○」と感じ、本当は「○○」を望んでいた。今はこの気持ちを「伝える・今は保留する・伝えない」のどれで扱うか、自分で選んだ。

現時点では、継続利用によって目指す状態は別のゴールとして設定しません。まずは1回の相談で、気持ちの整理と扱い方の選択まで完了できることをMVPの中心にします。

### ゴールに含めないもの

- パートナーとの関係改善の保証
- 相手へのメッセージの自動送信
- AIによる代理決断
- 医療的な診断・治療・カウンセリングの代替
- 話し始めの一文・伝え方メモの生成
- AIとの会話練習
- 選択後の行動計画を必須で作成すること

## 5. 解決方法と利用の流れ

最初からすべてを文章で入力させず、選択肢と短い自由記述を組み合わせて、考え始める負担を減らします。

1. 五つの相談テーマと「その他」から、今の気持ちに近いものを一つ選ぶ
2. 選んだテーマをきっかけに、具体的な出来事や言葉を入力する
3. AIが出来事を一問ずつ確認し、「何があったか」「何が気になったか」を本人が確認・編集する
4. 近い感情を一つ選び、自分の言葉で具体的に補う
5. AIとの対話で、本音・背景・望みを整理する
6. AIがまとめた整理結果を本人が確認・編集・承認する
7. 「伝える・今は保留する・伝えない」から一つを選ぶ
8. 判断理由を残したい場合だけ入力する
9. 整理メモを保存するか、保存せず終了するか選ぶ

出来事の追加質問は原則1〜2問とし、ユーザーが希望する場合は最大3問までとする仮案です。最大数に達した後は対話を増やさず、本人が要約を編集して次へ進めるようにします。

### 選択肢の仮案

- **相談テーマ**：会話・連絡・愛情表現／暮らし・家事・生活習慣／お金・負担の分け方／態度・思いやり・距離感／将来・価値観・二人の関係／その他
- **感情**：寂しい／悲しい／不安／怒り・いら立ち／モヤモヤ・違和感／傷ついた／その他・まだよく分からない

これらは正確に分類するためではなく、気持ちを考え始める入口です。名称と分け方はチーム確認と画面試用で調整します。

## 6. MVPの範囲

### MVPに含める

- ユーザー登録・ログイン・ログアウト
- 利用前の注意と外部AIへの送信に関する案内
- テーマ選択と具体的な内容の入力
- 出来事・感情・本音・背景・望みを整理するAIとの段階的な対話
- 出来事の要約と整理結果の確認・編集・承認
- 「伝える・今は保留する・伝えない」の単一選択
- 判断理由の任意入力
- 承認済み整理メモの保存・一覧・詳細・個別削除
- 保存せず相談を終了する選択
- 退会時の関連メモ一括削除
- プランの確認、決済、解約、利用上限の切り替え
- 安全・プライバシーに関する案内

### MVPに含めない

- 選択後の「次の一歩」や行動計画の入力
- 話し始めの一文・伝え方メモの生成
- AIとの会話練習
- 実行後の自動フォローアップ・通知
- RAG・ベクトル検索、過去メモのAI分析
- 本文検索、複数条件検索、メモ比較、簡易集計
- 相手へのメッセージ自動送信
- 管理者向けの本文閲覧画面・本格的な監査ログ基盤
- 本番運用を想定した複雑な課金管理

「余裕があれば追加する機能」は現時点では設定しません。まず中心となる相談・選択・保存と、スクールMUST要件への対応を完成させます。追加機能は中心機能の完成後に、あらためてチームで決めます。

## 7. 画面構成

画面の役割・遷移・構成理由・画像は、[ぽろり MVP画面ワイヤーフレーム案](porori-mvp-wireframes.md)を確認してください。

~~~text
登録・ログイン
  ↓
ホーム → 利用前の注意 → テーマ選択 → 具体的な内容の入力
  ↓
出来事の整理・要約確認 → 感情の選択・具体化 → 本音・背景・望みの整理
  ↓
整理結果の確認・編集 → 扱い方の選択 → 判断理由・保存確認
  ↓
保存メモ詳細 または 保存せずホームへ
~~~

保存メモ一覧、プラン、設定・退会はホームから開きます。相談内の各段階は、別々の独立機能ではなく、一つの相談画面内で表示内容が順に変わる想定です。

## 8. 保存と安全性の基本方針

- 相談中の会話全文・入力原文・未承認の内容は、自社DB・Redis・ログへ保存しない
- 本人が確認・編集・承認し、保存を選んだ整理メモだけを保存する
- 保存する自由記述は、実績のある方法で暗号化する
- API側で所有者を確認し、本人以外がメモを閲覧・変更・削除できないようにする
- 保存前の確認、保存しない選択、個別削除、退会時の一括削除を提供する
- 外部AIへ内容を送信することと、実名・住所・連絡先などを入力しないことを事前に案内する
- 「どこにも保存されない」とは説明せず、OpenRouterとモデル提供者の保持・学習方針を確認する
- 医療・心理相談の代替ではないことを示し、つらさが強い場合の専門窓口を案内する

## 9. スクール要件と技術の位置づけ

スクールテキスト上の要件と、ぽろり。での採用候補を分けて扱います。

| 項目 | スクール上の位置づけ | ぽろり。での現時点の案 |
| --- | --- | --- |
| コンテナ | MUST | Docker Composeを候補とする |
| キャッシュサーバー | RedisまたはMemcachedがMUST | Redisを候補とする |
| 決済 | 決済機能の組み込みがMUST | Stripeを候補とする |
| データベース | PostgreSQLの指定はない | PostgreSQLを候補とする |
| LLM | ADVANCED | ぽろり。の中心機能としてOpenRouter経由で利用する |
| デプロイ・HTTPS | ADVANCED | MVP完成条件には含めず、対応範囲は別途決める |

このほか、Webアプリ、フロントエンドとバックエンドの分離、セキュリティ対策、単体テスト、テスト設計書・テストシナリオ、開発環境と本番環境のログ出し分けにも対応します。

### 現時点の技術候補

| 領域 | 候補 |
| --- | --- |
| フロントエンド | Next.js / TypeScript |
| バックエンド | FastAPI / Python |
| データベース | PostgreSQL |
| キャッシュ・利用回数制限 | Redis |
| AI連携 | OpenRouter |
| 決済 | Stripe test mode |
| 自由記述の暗号化 | FastAPI側でのアプリ層暗号化 |
| 開発環境 | Docker Compose |

上記は技術選定資料と意見メモにある現時点の候補であり、チームの最終決定ではありません。採用理由、比較候補、認証・ORM・暗号化ライブラリ・テスト方式などは、技術選定資料の確定後に本企画案へ反映します。

## 10. プランと決済

決済機能はスクールMUST要件です。ぽろり。ではStripeを候補とし、無料・有料で相談回数と保存件数を切り替える案を検討しています。

- 無料でも、開始できた1回の相談は途中で止めず、扱い方の選択まで完了できるようにする
- 価格、相談回数、保存件数は現時点では確定しない
- StripeテストモードでMUST要件を満たせるかは講師へ確認する
- 有料契約中の退会では、解約とデータ削除の順序・失敗時の扱いを実装前に決める

## 12. MVPの完成条件

- ユーザーが相談を開始し、段階的な整理を最後まで進められる
- 自分の感情と望みを確認・編集・承認できる
- 「伝える・今は保留する・伝えない」のどれで扱うか自分で選べる
- 保存する場合は、本人が承認した整理メモだけを安全に保存・閲覧・削除できる
- 保存しない場合も相談を完了できる
- 会話全文や未承認の入力原文が自社DB・Redis・ログに残らない
- 本人以外のデータを操作できない
- 決済・キャッシュサーバーを含むスクールMUST要件への対応を確認できる
- 主要な正常系・異常系のテスト結果を示せる

## 13. チームで確認したいこと

1. 選択後に別の「次の一歩」を設けず、「扱い方の選択・記録」までをMVPのゴールとする案でよいか
2. 最初に表示する五つのテーマと、感情候補の名称・選択方法は適切か
3. 出来事の追加質問を原則1〜2問、希望時は最大3問とする案でよいか
4. 感情選択後の自由記述と、扱い方を選んだ理由を必須・任意のどちらにするか
5. 利用前の注意の表示頻度と、保存後の整理メモを再編集できるかをどうするか
6. 無料・有料の差を相談回数と保存件数とするか
7. 有料契約中の退会では、解約成功後にアカウントと保存データを削除する流れでよいか

## 14. 講師に確認したいこと

1. Stripeのテストモードで、MUSTの「決済機能を組み込む」を満たした扱いになるか
2. デプロイしない場合、開発環境と本番環境のログの出し分けをどのように確認するか

## 1. 目的・対象範囲

実装完了後にテスト観点を考えるのではなく、MVP仕様と画面・API設計の初稿をもとに、正常系・異常系・セキュリティ・非保存確認の観点を先に整理する。Sprint3以降のテスト実装Issueと単体テストへ引き継ぐ。

### 対象に含める
- MVPの中心フロー（登録・ログイン〜相談〜扱い方の選択〜保存・削除）
- 入力エラー、状態の矛盾、認証・認可、AI異常出力
- 暗号化・削除・非保存・ログ禁止
- Stripeテスト決済、Redisによる利用回数制限

### 対象に含めない
- テストコードの実装
- 全ブラウザ・全端末の網羅
- MVP外機能（伝え方メモ、会話練習、通知、RAG、メモ再編集など）
- 技術検証や設計で未確定の仕様を、本書で独自に確定すること

## 3. テスト区分・優先度・IDの定義

### 3.1 テスト区分

| 区分 | 内容 | 主な手段（想定） |
| --- | --- | --- |
| 単体 | 関数・スキーマ・APIハンドラ単位。DB・Redis・外部サービスはモック | pytest |
| 結合 | API＋PostgreSQL＋Redisを実物でつなぐ。AI（OpenRouter）・Stripe・Firebaseはモック（要確認 Q-20） | pytest＋Docker Compose |
| シナリオ | 画面操作でユーザーフローを通す。Firebase・Stripeテストモード・OpenRouterは実物を使い、外部サービスとの接続を確認する | 手動（ツールは要確認 Q-19） |

外部サービスとの接続そのものは技術検証（#4〜#7）で確認済みのため、結合テストでは自分たちのコードの分岐・保存・非保存を確認し、実物との接続はシナリオテストで確認する。

### 3.2 優先度

| 優先度 | 基準 |

| P1 | 重要だが、P0の完了後でもよい |
| P2 | 余裕があれば実施する |

## 7. テストデータ方針

- 実在の相談内容・個人情報は使用しない
- 本文には検出用の目印文字列（例：`PORORI_TEST_MARKER_001`）を含めた架空文を使う
- 決済はStripe公式のテストカードのみ使用する
- 認証は架空の検証用ユーザーA・Bを使う
- 外部サービスを実物で呼ぶシナリオテストは、実施回数と費用の上限を事前に決めて記録する（OpenRouterは課金あり）

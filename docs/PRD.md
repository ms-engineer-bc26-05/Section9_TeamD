### 1. プロジェクト概要（Overview）

- **プロダクト名**：ぽろり。
- **作成日**：2026年9月19日
- **概要**：パートナーとの関係を大切にするあまり、不満や本音を自分の中だけで処理してしまう人が、AIとの対話で気持ちを整理し、「伝える・今は保留する・伝えない」を自分で選べるところまで進めるWebアプリ
- **開発体制**：5人チーム、4週間
- **位置づけ**：スクールのチーム開発課題（最終プロジェクト）
- **提供形態**：スマートフォンでの利用を中心に想定したWebアプリ

### 2. 背景（Background）

関係を大切にする人ほど不満を自分で消化しようとし、その結果、自分の気持ちが分からなくなる、という課題を扱う。

#### なぜ必要か

- 相手を尊重するからこそ「不満は自分で消化すべき」と考え、気持ちを後回しにする人がいる。
- 一人で処理し続けると、自分が何を感じ、何を望んでいるのか分からなくなる。その結果、抱え込み、感情の爆発、すれ違いが起きる。
- 家族や友人には評価や人間関係があって話しづらく、パートナー本人にもまだ話せない。利害関係のない「第三の場所」が必要になる。

#### 現在の課題

| 既存の手段 | 足りない点 |
| --- | --- |
| 日記・メモ | 自由に書けるが、整理から選択までの道筋がない |
| ChatGPTなどの汎用AI | モヤモヤの最中に指示文を考え、順序立てて振り返る負担が大きい |
| 友人・家族への相談 | 評価や関係性を気にして話しづらい |

さらに、気持ちを整理できても「伝えるのか、保留するのか、伝えないのか」を決められず止まってしまう人がいる。

#### 根拠と検証事項

- 厚生労働省「今の気持ちを書いてみる」では、気持ちを書き出すと悩みと距離を取れ、自分で新しい選択肢に気づきやすくなると紹介されている。
- 次の点は資料だけでは証明できないため、開発初期のヒアリングや画面試用で確かめる。
  - 身近な人や汎用AIでは相談しづらい場面が実際にあるか
  - 段階的な問いかけで感情と望みを分けやすくなるか
  - 整理後の「選択」を負担ではなく支援と感じるか

### 3. 目的・ゴール（Goals / Objectives）

ゴールは「気持ちの整理」で、「伝える・今は保留する・伝えない」を自分で選べるところまでをその範囲に含める（チーム決定）。

#### プロダクトゴール

> 自分の感情と本当の望みを言葉にし、その気持ちを「伝える・今は保留する・伝えない」のどれで扱うかを自分で選べるところまで整理できること。

1回の利用後に、ユーザーが次の内容を自分の言葉で言える状態を目指す。

> 私はこの出来事で「○○」と感じ、本当は「○○」を望んでいた。今はこの気持ちを「伝える・今は保留する・伝えない」のどれで扱うか、自分で選んだ。

ぽろり。は、関係悪化への恐れをなくすアプリではない。恐れがあっても自分の気持ちを置き去りにしないためのアプリである。

継続利用によって目指す状態は、現時点では別ゴールとして設定しない。まずは1回の相談で、気持ちの整理と扱い方の選択まで完了できることをMVPの中心とする。

#### ゴールに含めないもの

- 関係改善の保証
- 相手へのメッセージ自動送信
- AIによる代理決断
- 医療的な診断・治療・カウンセリングの代替
- 話し始めの一文・伝え方メモの生成（伝え方支援）
- AIとの会話練習
- 選択後の行動計画・「次の一歩」の入力を必須とすること（#2決定：入力自体を求めない）

> Issue #2の決定により、選択後に別の「次の一歩」の入力は求めない方針を確定した。整理メモの保存も相談完了の必須条件としない。
>
> なお、Issue #2の決定事項No.1・No.3〜No.7は見直し条件なしで確定。No.2（訂正・再確認の上限回数）とNo.8（無料・有料プランの具体値）は方向性のみ確定で、それぞれ技術検証・画面試用後、Issue #6のStripe検証後に見直しの可能性がある（詳細は5節）。

#### KPI案（目標値はチームで設定）

| 指標 | 内容 |
| --- | --- |
| 整理完了率 | 相談開始から整理結果の承認まで到達した割合 |
| 選択決定率 | 「伝える・今は保留する・伝えない」のいずれかを選べた割合 |
| 利用前後の自己評価 | 利用前後に3問を比較する（今の感情を説明できるか／本当はどうしたいか説明できるか／扱い方を自分で選べているか） |
| 保存率 | 承認した整理メモを保存した割合 |

#### プロジェクトとしての達成条件

- スクールのMUST要件（Docker Compose、PostgreSQL、Redis、Stripeテスト決済、テスト設計書など）を満たす。
- 会話全文を自社DB・Redis・ログに残さず、保存する自由記述は暗号化する。

### 4. 対象ユーザー（Target Users）

対象は、パートナーとの関係を大切にしているからこそ、不満や本音を抱え込んでしまう人。「HSP」などの特性名ではなく、行動と状況で定義する。診断や自己認識の有無にかかわらず、同じ困りごとを持つ人に届けるため。

初期の調査・画面試用では20〜30代のパートナーがいる人を主な対象とするが、これは対象を具体化するための仮置きであり、利用を年齢で制限するものではない。

#### ペルソナ

- 嫌われることや関係悪化が怖く、本音を言いづらい
- 相手を尊重するあまり「自分で解決すべき」と考える
- 波風を立てないよう、自分の気持ちを後回しにする
- 我慢が続き、自分が何を感じているのか分からなくなっている
- 気持ちは分かっていても、どう扱うか決められない

#### 課題とニーズ

| 課題 | ニーズ |
| --- | --- |
| 出来事・解釈・感情・望みが混ざっている | 順序立てて分けて整理したい |
| 身近な人には相談しづらい | 評価や利害関係のない場所で整理したい |
| 伝えるべきか分からず動けない | 伝える・保留・伝えないを自分で納得して選びたい |
| AIに任せきりになるのは不安 | 内容を自分で確認・編集・承認したい |
| 内容が漏れるのが怖い | 会話を残さず、保存するものだけを本人が管理したい |

### 5. スコープ（Scope）

MVPは、一つの相談フローで「整理 → 選択 → 保存」までを通せる範囲に絞る。以下はIssue #2の決定記録（mvp-decisions.md）を反映した内容。

#### 含まれる機能（MVP）

| 機能 | 内容 | 決定状況（Issue #2） |
| --- | --- | --- |
| A. ユーザー登録・ログイン・ログアウト | アカウント作成とログイン。利用前の注意・外部AIへの送信に関する案内を含む | 確定（No.5） |
| B. テーマ選択 | 5テーマ（会話・連絡・愛情表現／暮らし・家事・生活習慣／お金の感覚の違い／気遣い・思いやりの伝わり方／将来・価値観・二人の関係）＋「その他」から最も近いものを一つ選ぶ | 確定（No.1） |
| C. AIによる段階的な相談 | 出来事 → 感情 → 本音・背景・望み の順に問いかける。出来事の追加質問は原則1〜2問、希望時は最大3問。AIの理解の訂正・再確認（訂正入力→AIが修正後の理解を提示→本人が再確認、までを1回と数える）は質問数のカウントに含めず、出来事を整理する工程全体で最大2回までとする。上限後はやり取りを増やさず、本人が要約を直接編集して次へ進む | 確定（No.2、回数はMVP初期値・見直し条件あり） |
| D. 感情の選択・具体化 | 8種類の感情候補（自分を責める気持ちを含む）から一つを選択。選択後は「自分の言葉で入力する」「うまく言葉にできない」のいずれかへの回答を必須とする | 確定（No.3・No.4） |
| E. 整理結果の確認・編集・承認 | AIが作成した整理結果を、本人が確認・修正して承認する | 現行前提（#2の確認事項には含まれない） |
| F. 扱い方の選択 | 「伝える・今は保留する・伝えない」から自分で選ぶ。理由の入力は任意 | 確定（No.6） |
| G. 整理メモの保存・管理 | 承認済みメモの暗号化保存、一覧、詳細、個別削除、退会時の一括削除。保存しない選択もできる。保存後の再編集はMVPでは対象外（拡張候補） | 確定（No.7） |
| H. プランと利用制限 | Stripeテストモードで決済・解約を実装し、有料・無料で相談回数と保存件数を切り替える。具体的な回数・価格はStripe検証後に決定し、固定値ではなく設定値として扱う | 暫定（No.8、方向性のみ確定・数値は要確認） |
| I. 安全・プライバシー対応 | 自分のデータだけを操作できるアクセス制御、会話本文を残さないログ、医療・心理相談の代替ではない旨の表示、相談窓口への導線（登録・ログイン画面を含む）を常時表示 | 確定（No.5＋現行前提） |

凡例：**確定**＝見直し条件なし。**確定（見直し条件あり）**＝方向性・初期値は確定だが、技術検証・画面試用の結果次第で見直す場合がある。**暫定**＝方向性のみ確定し、具体値は未決定。**現行前提**＝Issue #2の確認事項には含まれず、企画案・PRD初版からの前提。

#### 余裕があれば追加（現時点では未設定）

中心機能（相談・選択・保存）とスクールMUST要件への対応を完成させることを優先し、追加機能は中心機能の完成後にあらためてチームで決定する。

#### 含まれないもの

- 選択後の「次の一歩」や行動計画の入力
- 話し始めの一文・伝え方メモの生成、AIとの会話練習
- 実行後の自動フォローアップ・通知
- RAG・ベクトル検索、過去メモのAI分析
- 本文検索、複数条件検索、メモ比較、簡易集計
- 相手へのメッセージ自動送信
- 保存済み整理メモの再編集（MVP後の拡張候補）
- 管理者向けの本文閲覧画面・本格的な監査ログ基盤
- 本番運用を想定した複雑な課金管理

### 6. ユーザーストーリー（User Stories）

「ユーザーとして、○○できるようにしたい。なぜなら△△だから。」の形式で、五つの場面に分ける。

#### 整理する

- ユーザーとして、モヤモヤをそのまま入力できるようにしたい。なぜなら、何がつらいのか分からない状態でも始めたいから。
- ユーザーとして、出来事・感情・本音・望みを順に問いかけてもらいたい。なぜなら、一人だとそれらが混ざってしまうから。
- ユーザーとして、感情をうまく言葉にできないときも次へ進めるようにしたい。なぜなら、言葉にできないこと自体を理由に立ち止まりたくないから。
- ユーザーとして、AIがまとめた整理結果を確認・編集・承認したい。なぜなら、自分の気持ちをAIに決めつけられたくないから。
- ユーザーとして、AIの理解が違うときは訂正し、再確認したい。なぜなら、間違った前提のまま整理を進めたくないから。

#### 選ぶ

- ユーザーとして、整理した気持ちを「伝える・今は保留する・伝えない」から選べるようにしたい。なぜなら、必ず伝えるべきだとは限らず、自分のペースで決めたいから。
- ユーザーとして、「伝えない」を選んでもそれを我慢ではなく自分の判断として確認したい。なぜなら、納得して選んだ形にしたいから。
- ユーザーとして、選んだ理由を書きたいときだけ書けるようにしたい。なぜなら、理由を言葉にできるとは限らないから。

#### 保存・管理する

- ユーザーとして、残したい整理メモだけを保存するかどうか選べるようにしたい。なぜなら、デリケートな内容を必要以上に残したくないから。
- ユーザーとして、保存したメモを一覧・詳細で見返し、個別に削除できるようにしたい。なぜなら、自分の気持ちの傾向を振り返りたい一方で、消したいときは消したいから。
- ユーザーとして、退会時に自分のメモを一括で削除できるようにしたい。なぜなら、やめた後にデータが残るのは不安だから。

#### 安心して使う

- ユーザーとして、自分のメモを他の人に見られないようにしたい。なぜなら、恋愛や家庭の事情など、知られたくない内容を書くから。
- ユーザーとして、このアプリが医療・心理相談の代替ではないと分かり、必要なときに専門窓口へ辿り着けるようにしたい。なぜなら、つらさが強いときはアプリだけでは足りない場合があるから。

#### プランを使う

- ユーザーとして、無料でも1回の相談を最後まで完結させたい。なぜなら、試して価値を確かめてから有料にするか決めたいから。
- ユーザーとして、有料プランで相談回数と保存件数を増やし、いつでも解約できるようにしたい。なぜなら、継続して振り返りたくなったときに使いたいから。

### 7. 画面設計（Wireframes / UI 設計）

具体的な文言・配置・選択肢は Issue #9（画面設計）で決定する。本節では相談フロー全体の構成のみを示す。

```text
登録・ログイン
  ↓
ホーム → 利用前の注意 → テーマ選択 → 具体的な内容の入力
  ↓
出来事の整理・要約確認 → 感情の選択・具体化 → 本音・背景・望みの整理
  ↓
整理結果の確認・編集 → 扱い方の選択 → 判断理由・保存確認
  ↓
保存メモ詳細 または 保存せずホームへ
```

保存メモ一覧、プラン、設定・退会はホームから開く。相談内の各段階は、別々の独立画面ではなく、一つの相談画面内で表示内容が順に変わる想定。

詳細な画面ワイヤーフレームは `porori-mvp-wireframes.md` を参照。

### 8. 非機能要件（Non-functional Requirements）

#### セキュリティ・プライバシー

- 相談中の会話全文・入力原文・未承認の内容は、自社DB・Redis・ログへ保存しない
- 本人が確認・編集・承認し、保存を選んだ整理メモだけを保存する
- 保存する自由記述は、実績のある方法で暗号化する
- API側で所有者を確認し、本人以外がメモを閲覧・変更・削除できないようにする
- 保存前の確認、保存しない選択、個別削除、退会時の一括削除を提供する
- 外部AIへ内容を送信することと、実名・住所・連絡先などを入力しないことを事前に案内する
- 「どこにも保存されない」とは説明せず、OpenRouterとモデル提供者の保持・学習方針を確認する
- 医療・心理相談の代替ではないことを示し、つらさが強い場合の専門窓口を案内する

#### パフォーマンス・対応環境

未定。技術検証（Issue #6ほか）の結果を踏まえ、後続Issueで追記する。

- 画面上の最終的な文言・配置・見た目（Issue #9）
- API・DBの具体的なデータ構造（Issue #10、#11）
- 無料・有料プランの価格、相談回数、保存件数（Issue #6のStripe検証結果を踏まえたプラン仕様検討時に決定。方向性〔相談回数・保存件数を候補とし、固定値化しない〕は確定済み）

#### 講師確認が必要な事項

- デプロイしない場合、開発環境と本番環境のログの出し分けをどのように確認するか（未回答）

> Stripeテストモードで決済MUST要件を満たせるかは講師へ確認済み（満たす扱いで進行）。

#### その他のリスク

- サービスの有効性（気持ちの整理につながるか）は資料だけでは証明できず、ヒアリング・画面試用で検証する必要がある（仮説段階）
- 認証・暗号化・OpenRouter連携などの技術検証が未了であり、検証結果次第で技術候補・実装方針が変わる可能性がある
- 4週間という開発期間に対し、AI対話・決済・暗号化など検証項目が多く、スケジュールリスクがある

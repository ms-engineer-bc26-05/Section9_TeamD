# GitHub運用ルール

このドキュメントでは、Team Dの最終プロジェクト「ぽろり。」におけるGitHubの運用ルールを定めます。

アプリの概要、使用技術、環境構築については、内容が確定した段階でルートの`README.md`へ追記します。

> [!NOTE]
> このルールは、チームで合意した内容や開発状況に応じて更新します。

## 1. 基本的な作業の流れ

開発・技術検証・ドキュメント更新は、原則として次の流れで進めます。

```text
Issueを確認
↓
最新のdevelopから作業ブランチを作成
↓
Issueの範囲内で作業・確認
↓
Pull Requestを作成
↓
Discordで確認担当者へ作成報告
↓
確認担当者がPull Request上でレビュー
↓
Issueに記載された確認担当者のうち1名以上がApprove
↓
Pull Request作成者がdevelopへSquash and merge
↓
作業ブランチを削除
```

子Issueの基本単位は次のとおりです。

```text
1 子Issue = 主担当1名 = 1 作業ブランチ = 1 Pull Request
```

1つの子Issueを複数人で共同実装しません。確認担当と相談先は主担当を支援しますが、共同実装者ではありません。

親Issueは、複数の子Issueの進捗・依存関係・ブロック状況を管理するために使用します。親Issue自体では、原則として実装ブランチやPull Requestを作成しません。

早期導入や段階的な確認のため、1つのIssueを複数のPull Requestへ分ける必要がある場合は、作業開始前に理由・順番・各Pull Requestの範囲・IssueをCloseするPull Requestを明記し、チームで確認します。複数のPull Requestを同時並行では進めず、前のPull Requestをマージしてから次へ進みます。主担当は途中で分割しません。

以下は禁止します。

- `main`への直接コミット・直接push
- `develop`への直接コミット・直接push
- APIキー、秘密鍵、パスワード、トークン、`.env`のpush
- 実際の相談内容や個人情報を、Issue・Pull Request・コード・テストデータへ記載すること
- チームへの共有なしにforce push、共有ブランチのrebase、ブランチ削除を行うこと

---

## 2. ブランチの役割

### `main`

完成版・発表版など、安定した状態を管理するブランチです。

通常の作業では使用せず、MVPが発表・公開できる状態になった段階で、`develop`からPull Requestを作成して反映します。

### `develop`

各メンバーの変更を集約する開発用ブランチです。

通常のPull Requestは、`develop`をマージ先にします。

### 作業ブランチ

Issueごとの作業を行うブランチです。必ず最新の`develop`から作成します。

---

## 3. ブランチ名

次の形式を基本とします。

```text
種別/issue-{Issue番号}-{作業内容}
```

例：

```text
feature/issue-12-emotion-selection
fix/issue-24-payment-error
docs/issue-8-update-prd
chore/issue-10-docker-setup
spike/issue-5-openrouter-verification
```

| 種別 | 用途 |
| --- | --- |
| `feature` | 新機能の追加 |
| `fix` | 不具合の修正 |
| `docs` | ドキュメントの追加・修正 |
| `chore` | 環境構築・設定など |
| `spike` | 採用可否を判断するための技術検証 |
| `refactor` | 動作を変えないコード整理 |
| `test` | テストの追加・修正 |

## 4. Issue

作業開始前にIssueを作成し、担当者が一人で作業を始められる程度まで内容を具体化します。

Issueには、原則として次を記載します。

- 目的・背景
- 作業範囲
- やらないこと
- 作業手順
- 成果物
- 完了条件
- 依存するIssue・前提条件
- 主担当
- 確認担当
- 相談先
- 親Issue管理担当
- 期限
- このIssueで決定する事項
- 注意事項・参考資料

### 親Issueと子Issue

親Issueは、複数の子Issueをまとめ、全体の進捗・依存関係・ブロック状況を確認するために使用します。

親Issue管理担当は、次を行います。

- 子Issueを親Issueへリンクする
- 子Issueの進捗を更新する
- 依存関係とブロック状況を確認する
- 担当・順番・期限へ大きな変更が必要な場合にチームへ共有する

親Issue管理担当であることを理由に、子Issueの実装を自動的に引き取ることはありません。

子Issueは、主担当1名が一人で作業を進められる単位へ分割します。

### 担当区分

| 区分 | 作業責任 |
| --- | --- |
| 主担当 | Issueの実作業、判断事項の取りまとめ、テスト、Pull Request作成、Issue更新を行う1名 |
| 確認担当 | Pull Requestをレビューし、完了条件・変更範囲・確認結果を確認する。共同実装者ではない |
| 相談先 | 技術検証や関連機能の知識を共有する。決定や実装を代行する担当ではない |
| 親Issue管理担当 | 子Issueのリンク、進捗、依存関係、ブロック状況を管理する |

### 未確定事項の決定区分

#### A：主担当が決定できる

コーディング規約、設計書、共通ディレクトリ構成、他機能との契約を変更しない範囲で、担当機能内だけに閉じる命名・関数分割・補助ファイル構成を主担当が決定できます。

APIのパス・リクエスト・レスポンス、DBのテーブル・カラム、画面遷移、利用者に見える文言、共通ディレクトリ構成、他機能へ公開する型やServiceはAに含めません。

#### B：関係者へ確認して主担当が決定する

他機能から利用する型やService関数、APIと画面のエラー対応、一時状態の保持時間、テスト方法、機能間の呼び出し方法など、依存する機能へ影響するものが該当します。

主担当が推奨案・理由・影響・回答期限を提示し、関係者の意見を取りまとめて決定します。

#### C：チーム確認が必要

次に該当する場合は、主担当が案を整理したうえでチームへ確認します。

- MVPの対象範囲を変更する
- プライバシー・セキュリティ方針を変更する
- 画面・API・DB契約を大きく変更する
- 決済条件や利用回数など、プロダクト仕様を変更する
- 担当・期限・依存関係を大きく変更する

意見が分かれて期限までに決定できない場合は、リーダーへ最終調整を依頼します。

「後続Issueで検討」とだけ記載せず、対応Issue・取りまとめ担当・確認相手・決定期限・記録先を明記します。

作業中にIssueの範囲を大きく超える対応が必要になった場合は、自己判断で範囲を広げず、別Issueへ分けるかチームへ相談します。

担当者が予定どおり対応できない場合は、チームメンバーで再分担を相談し、変更した担当をIssueへ記録します。MVPの範囲や中心価値に影響する変更は、チーム全体で確認します。

### Issueの更新

主担当は、次の場合にIssue本文またはコメントを更新します。

- 決定事項が確定した
- 作業範囲や完了条件に補足が必要になった
- 関連Issueへ契約を共有した
- ブロックが発生した
- テスト結果が出た
- 既知の制約や今後の改善候補が判明した

担当・作業範囲・依存関係・完了条件など、継続して参照する情報はIssue本文へ反映します。日付を伴う進捗・質問・テスト結果・ブロック報告はコメントへ記録します。コメントで確定した内容を継続して参照する場合は、Issue本文にも反映します。

担当・作業範囲・依存関係・完了条件を大きく変更する場合は、変更前にチームへ共有します。

### 不具合の管理

作業中のIssueの範囲内であり、完了条件を満たすために必要な修正は、元のIssue・Pull Requestで対応します。

次の場合は、不具合を発見した人が新しい不具合Issueへ記録します。

- 元のIssue・Pull Requestがマージ済み
- 別機能・別担当の変更が必要
- 原因調査や修正にまとまった時間が必要
- セキュリティ・プライバシー・データ消失に関係する
- 修正を後日に回す

不具合Issueには、発生した操作、期待する結果、実際の結果、再現手順、影響範囲、緊急度、関連Issue・Pull Requestを記載します。実際の相談内容や秘密情報は記載しません。

起票者が必ず修正するのではなく、優先度と影響を確認した後、主担当を1名設定します。

## 5. 作業開始時

作業開始前に、未コミットの変更がないか確認します。

```bash
git status --short
```

問題がなければ、最新の`develop`から作業ブランチを作成します。

```bash
git switch develop
git pull --ff-only origin develop
git switch -c feature/issue-12-emotion-selection
```

ブランチ作成後、現在のブランチを確認します。

```bash
git branch --show-current
```

未コミットの変更が表示された場合や、pullに失敗した場合は、そのまま次の操作へ進まずチームへ相談します。

---

## 6. 同時作業とコンフリクトの予防

- Issueごとに編集対象ファイルを明記する
- 原則として、複数人が同じファイルを同時に変更しないようIssueを分ける
- 機能・責務ごとにファイルを分け、各メンバーが並行して作業できる構成を検討する
- やむを得ず同じファイルを編集する場合は、作業範囲と順番を決め、作業前にDiscordで声をかける
- 主担当と確認担当を決める
- 確認担当は、可能であれば次に関連作業を担当する人とする
- 依存Issueと並行して進められる準備・設計・テスト作業がある場合は、Issueへ明記する
- 依存Issueの完了を待つ必要がある場合は、待機理由と開始条件をIssueへ明記する

### 共有ファイル

次の共有ファイルは、複数Issueから同時に変更しないようにします。

- `backend/app/main.py`
- `frontend/app/layout.tsx`
- `README.md`
- `compose.yaml`
- 共通設定ファイル
- GitHub ActionsのWorkflow
- マイグレーションの共通設定

共有ファイルを変更するIssueには、変更対象・主担当・変更する順番・先行Issue・後続Issueを明記します。最終接続は、結合Issueまたは接続担当を明記したIssueで行います。

### README更新

README更新が必要だと判明した場合は、各主担当が自分のIssueへ更新内容を記録します。

- 機能のPull RequestでREADMEを変更する場合は、Issueの作業範囲へ明記する
- 複数Issueから同時にREADMEを編集しない
- 共通環境構築に関する初期更新はIssue #35で行う
- アプリレビュー前の最終統合はIssue #64（Q-04）で行う
- 緊急更新が必要な場合は、編集担当者を1名決める
- 実装上の判断・テスト結果・制約は各Issue・Pull Requestへ記録し、Issue #64（Q-04）でREADMEへ集約する

技術検証では、OpenRouter・認証・Stripe・暗号化などの検証ごとに、コード・結果・記録先を分けます。複数の検証結果を比較して採用方針を決める作業は、各検証Issueとは別の統合Issueとして扱います。

これにより、検証担当者が同じファイルを編集することや、ほかの検証結果を待って作業が止まることをできるだけ避けます。

## 7. コミットとステージング

コミットは、意味のある変更単位で行います。無関係な変更を同じコミットへ混ぜません。

意図しないファイルの混入を防ぐため、原則として`git add .`は使用せず、対象を明示します。

```bash
git add frontend/src/example.tsx
git add docs/example.md
```

ステージング後は、必ず対象を確認します。

```bash
git status --short
git diff --cached --check
git diff --cached --name-only
```

コミットメッセージには、変更内容が分かる接頭辞を付けることを推奨します。

```text
feat: 感情選択画面を追加
fix: 決済失敗時の表示を修正
docs: PRDを更新
test: 認証APIのテストを追加
chore: Docker設定を追加
```

## 8. Pull Request

通常は、次の組み合わせでPull Requestを作成します。

```text
base: develop
compare: 作業ブランチ
```

Pull Requestには、対応Issue、変更内容、確認結果、レビューしてほしい点を記載します。

```markdown
## 対応Issue

Closes #

## 変更内容

-

## 対象外・未対応

-

## 動作確認

- [ ] Issueの完了条件を満たしている
- [ ] 対象のLint・テスト・ビルドを実行した
- [ ] 既存機能に明らかな影響がない
- [ ] 意図しないファイルが含まれていない
- [ ] 秘密情報や相談内容が含まれていない

## レビューしてほしいこと

- 確認担当:
- 希望する確認期限:
- 特に確認してほしい点:

## スクリーンショット

UI変更がある場合に添付します。

## 補足

- 確認できていないこと:
- 既知の問題:
- 代理確認者を設定した場合の担当者・理由:
```

実装途中で共有・相談したい場合は、Draft Pull Requestを使用します。

## 9. Pull RequestとDiscordの使い分け

レビュー内容、修正依頼、仕様に関する確認事項、対応結果は、履歴を残すためPull Request上へコメントします。

Pull Requestを作成した際は、Discordで確認担当者へ次を共有します。

- Pull Requestを作成したこと
- 対応したIssue
- 変更内容の概要
- 特に確認してほしい点
- Pull RequestのURL

Discord上だけでレビューを完結させず、Approveや修正内容はPull Request上に残します。

Discordで重要な仕様・方針が決まった場合は、IssueまたはPull Requestにも記録します。

---

## 10. レビューとApprove

Pull Request作成者以外のメンバーがレビューします。原則として、Issueに記載された確認担当者へ依頼します。

主な確認項目は次のとおりです。

- Issueの目的・完了条件を満たしているか
- Issueの範囲を超える変更がないか
- 意図しない変更や不具合がないか
- 必要な確認・テストが実行されているか
- 秘密情報や実際の相談内容が含まれていないか
- コードや設計が極端に分かりにくくなっていないか

分からない箇所は無理に判断せず、Pull Request上で質問します。

**Pull Request作成者以外の確認担当者から、最低1名のApproveを受けてからマージします。**

確認担当者が複数いる場合も、通常は最低1名のApproveでマージ可能です。セキュリティや複数領域にまたがる変更など、複数人全員の確認が必要な場合は、IssueとPull Requestへ事前に明記します。

認証・認可、暗号化・相談データの保存、決済、共通のAPI・DB設計、GitHub運用ルール、AIエージェントの共通ルールに関する変更は、複数人の確認対象とします。Issue作成時に確認担当者を複数名指定し、指定された確認担当者全員のApproveを得てからマージします。

作業開始後に複数人の確認が必要だと分かった場合は、Pull Request作成者または確認担当者がチームへ共有し、確認担当者を追加します。誰か一人の判断で確認を省略しません。

確認担当者は、Discordでのレビュー依頼から**原則24時間以内**を目安に、次のいずれかを一次反応として返します。

- レビューまたはApproveを行う
- 質問・確認事項を伝える
- レビューできる見込み時刻を伝える

24時間以内の対応が難しい場合はDiscordで共有し、必要に応じて確認担当者をチームで調整します。これは厳密な期限ではなく、レビュー待ちで作業が止まることを防ぐための目安です。

### 確認担当が期限までに対応できない場合

主担当は、Pull Request作成時に希望する確認期限を共有します。

確認担当が期限までに対応できない場合は、相談先または関連機能の担当者から代理確認者を1名決めます。

- Pull Request作成者本人は代理確認者にならない
- 代理確認者と変更理由をIssue・Pull Requestへ記録する
- 代理確認者は、交代対象となった確認担当者と同じ確認責任を持つ
- 複数人の確認が必須の場合、交代対象以外の必須確認者は省略しない
- 代理確認者がApproveした場合、当初の確認担当者による再レビューを必須としない

これは確認待ちで作業を止めないためのレビュー運用であり、1つのIssueを複数人で共同実装する運用にはしません。

## 11. レビュー後の修正

レビュー対応は、同じ作業ブランチで行います。同じブランチへpushすると、既存のPull Requestへ変更が反映されます。

修正後は、対応内容をPull Request上へコメントし、必要に応じて再レビューを依頼します。

レビューで意見が分かれた場合は、Pull Request上で根拠・要件・懸念点を確認します。2往復しても合意できない場合は、第三のチームメンバーへ確認を依頼します。

スクール要件、セキュリティ、プライバシー、外部サービスの利用条件に関する判断がチーム内で解決できない場合は、講師へ相談します。結論が出るまではマージせず、決定理由をIssueまたはPull Requestへ記録します。

---

## 12. マージ

最低1名のApproveを受け、必要な確認が完了したら、原則としてPull Request作成者本人がマージします。

Pull Request作成者がすぐに対応できず、ほかのメンバーの作業が止まる場合に限り、Approveした確認担当者が代理でマージしても構いません。

代理でマージする場合は、次をすべて確認します。

- 必要なApproveを受けている
- 必須のテスト・確認が完了している
- 未解決のレビューコメントがない
- Pull Request作成者から、追加修正の予定が共有されていない
- 代理でマージする理由をPull Requestへコメントしている

マージ方法は、**`Squash and merge`**に統一します。

マージ後は、GitHub上の作業ブランチを削除します。ローカルブランチは`develop`を最新化した後に削除します。

## 13. 作業中に`develop`が更新された場合

自分の作業に影響する変更が`develop`へ入った場合は、必要に応じて作業ブランチへ取り込みます。

```bash
git fetch origin
git merge origin/develop
```

共有済みの作業ブランチでは、原則としてrebaseを使用しません。

コンフリクトが発生し、どちらの変更を残すべきか判断できない場合は、自己判断で他メンバーの変更を削除せず、チームへ相談します。

---

## 14. force pushと危険な操作

force pushは、リモートの履歴を強制的に書き換える操作です。他メンバーのコミットを消す可能性があるため、通常は使用しません。

次の操作は、自己判断で実行しません。

- `git push --force`
- `git reset --hard`
- 共有ブランチの`git rebase`
- リモートブランチ・タグの削除
- 本番環境や共有DBのデータ削除

Git操作を誤った場合は、追加操作で直そうとせず、現在の状態と実行したコマンドをチームへ共有します。

## 15. 秘密情報と相談データ

以下はGitHubへ登録しません。

- `.env`、`.env.local`、`.env.production`など
- OpenRouterのAPIキー
- Firebaseの秘密鍵・認証情報
- Stripeの秘密鍵・Webhookシークレット
- DBパスワード
- 整理メモの暗号化鍵
- アクセストークン・IDトークン
- 実際の相談内容、個人情報、会話全文

リポジトリには、環境変数名とダミー値だけを記載した`.env.example`を登録します。

テスト・画面例・Issue・Pull Requestでは、実在の人物や相談内容を使用せず、架空のデータを使います。

「ぽろり。」では、会話全文をDB・Redis・ログへ永続保存しません。保存対象は、ユーザーが確認・編集し、保存に同意した整理メモだけとします。

秘密情報をpushした、またはpushした可能性がある場合は、ファイルを削除するだけで済ませず、すぐにチームと講師・スクール事務局へ共有します。

## 16. テスト・品質

- 変更対象に対応するテストがあれば実行する
- 振る舞いを追加・変更した場合は、必要なテストも追加・更新する
- 実行したコマンドと結果をPull Requestへ記録する
- 未確認事項は「未確認」と明記する
- 技術検証は、成功だけでなく失敗・停止理由・未確認事項も記録する

Lint・Formatter・Test・Buildの具体的なコマンドは、技術構成と初期環境が確定した段階で追記します。

GitHub Actionsのワークフローと実行コマンドが確定した後は、`develop`へのマージ条件として必要なActionsの成功を必須チェックに設定します。設定にはAdmin権限が必要な場合があるため、リポジトリ管理者へ依頼します。それまでは、Pull Requestのチェックリストと実行結果を確認します。

## 17. AIエージェントを利用する場合

使用するAIエージェントに対応したルールを、作業開始前に確認します。

- Codex・Claude Codeなどの共通ルール：[`AGENTS.md`](../AGENTS.md)
- Claude Code固有の入口：[`CLAUDE.md`](../CLAUDE.md)。`AGENTS.md`と本ファイルを参照する

AIへ作業を依頼する場合も、Issueの範囲、承認、秘密情報、レビューのルールは変わりません。

外部APIを使う技術検証では、実行前にIssueまたは検証記録へ、対象モデル・テストケース・最大リクエスト数・概算上限額・成功条件・停止条件を記載します。上限を超える追加検証は、チーム確認後に実行します。

## 18. 困ったとき

次の場合は、自己判断だけで進めずチームへ相談します。

- Issueの範囲を大きく超える変更が必要になった
- 他のIssue・機能・設計へ影響する変更が必要になった
- 他メンバーの変更を削除・大幅修正する必要がある
- Git操作を誤った
- コンフリクトの解消方法が分からない
- 秘密情報や相談内容をpushした可能性がある
- 複数の方法があり、チームで統一した方がよい
- 技術検証の停止条件に該当した

問題が大きくなる前に共有することを優先します。

## 決定事項まとめ

| 項目 | 運用ルール |
| --- | --- |
| 通常のマージ先 | `develop` |
| 子Issue・主担当・ブランチ・PR | 原則として1対1。複数PRへ分ける場合は理由・順番・範囲・CloseするPRを事前確認 |
| 親Issue | 子Issueの進捗・依存関係・ブロック状況を管理し、原則として実装ブランチ・PRを作成しない |
| 担当区分 | 主担当・確認担当・相談先・親Issue管理担当を区別 |
| 未確定事項 | A・B・Cの決定区分と、担当・確認相手・期限・記録先を明記 |
| Issue更新 | 決定、範囲補足、契約共有、ブロック、テスト結果、制約・改善候補を記録 |
| 不具合 | 完了条件内は元Issue・PR、マージ後・別機能・まとまった調査が必要な場合は新規Issue |
| 共有ファイル・README | 変更担当と順番を決め、複数Issueから同時編集しない |
| Approve | Pull Request作成者以外の確認担当者から最低1名が必要。複数人必須の場合はIssue・PRへ明記 |
| 確認担当 | Issueに記載。期限までに難しい場合は、相談先・関連機能担当者から代理確認者を決めて記録 |
| レビュー一次反応 | Discordでの依頼から原則24時間以内を目安に、レビュー・質問・対応見込みのいずれかを共有 |
| マージ実行者 | 原則としてPull Request作成者本人。作業が止まる場合は、条件を満たした確認担当者の代理マージ可 |
| マージ方法 | `Squash and merge` |
| `develop`の取り込み | `merge`を使用 |
| `main`・`develop` | 直接コミット・直接push禁止 |
| レビュー内容 | Pull Request上へ記録 |
| PR作成報告 | Discordで確認担当者へ概要とURLを共有 |
| 秘密情報・相談内容 | GitHub・ログへ記載しない |
| 技術検証 | `spike/`ブランチを使用し、結果と停止理由を記録 |
| CI | GitHub Actions確定後、必要なチェックの成功を`develop`へのマージ条件に設定 |

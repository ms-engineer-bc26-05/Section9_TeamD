- スクールMUST：スクールから求められる要件。

## 3. プロジェクト概要

### システム名

ぽろり。

### 目的・背景

パートナーとの関係を大切にするあまり、不満や本音を抱え込み、
自分の感情や望みを整理しにくい人を支援するWebアプリである。

AIとの対話を通じて、出来事・感情・本音・背景・望みを整理し、
その気持ちを「伝える・今は保留する・伝えない」から本人が選べるようにする。

相手に伝えることを強制せず、関係改善の保証、
AIによる代理決断、医療・心理相談の代替は行わない。

### MVPの相談完了条件

ユーザーが出来事・感情・本音・背景・望みの整理結果を確認し、
気持ちの扱い方を自分で選べた状態を相談完了とする。

- 整理メモの保存は、相談完了の必須条件ではない。
- 扱い方を選んだ理由は任意入力とする。
- 選択後に別の「次の一歩」の入力は求めない。
- どの扱い方を選んでも相談を完了できる。

### 開発体制

- 開発チーム：Team D
- 開発人数：5名
- 開発期間：約1か月
- Webアプリケーションとして開発する。

## 4. 用語定義

| 用語 | 定義 |
| --- | --- |
| 相談 | 気持ちを整理する一連の利用。回数を消費する時点と終了条件の詳細はAPI設計と確認する |
| 整理結果 | 出来事・感情・本音・背景・望みなどをまとめた内容。表示された時点では保存済みとは限らない |
| 承認 | 整理結果が本人の気持ちに合っていることを確認して確定する操作 |
| 保存同意 | 承認した内容を整理メモとして保存することを本人が選ぶ操作 |
| 整理メモ | 本人が承認し、保存に同意した整理結果と扱い方などの記録 |
| 扱い方 | 「伝える・今は保留する・伝えない」の選択 |
| 追加質問 | 気持ちの整理に必要な情報を補うためのAIの質問 |
| 訂正・再確認 | AIの理解のずれを直す操作。追加質問とは別に回数を管理する方針 |
| 利用権限 | ユーザーが利用できるプラン・機能・有効期間。決済記録とは区別する |

承認と保存同意は別の意味を持つ。
具体的な画面操作・API上の表現は、画面・API設計で統一する。

## 5. ユーザーの利用フロー

### 利用前の状態

1. パートナーとの出来事で不満やモヤモヤを感じる。
2. 関係悪化への不安などから、本人や身近な人へ相談できない。
3. 出来事・解釈・感情・望みが混ざり、整理しにくい。
4. 気持ちをどう扱うか決められず、抱え込んでいる。

### アプリでの基本フロー

以下は機能の流れであり、画面の分割数や確定した操作順序を示すものではない。

1. ユーザー登録・ログインを行う。
2. 利用上の注意と外部AIへの情報送信について確認する。
3. 相談テーマを選び、出来事を入力する。
4. AIとの対話で出来事を整理し、理解のずれを訂正できる。
5. 感情を選び、自分の言葉で具体化するか、
   「うまく言葉にできない」を選ぶ。
6. 本音・背景・望みを一問ずつ、自分の言葉で整理する。
   背景を整理できない場合は空欄を許容し、AIが推測して補わない。
7. 本音・背景・望みを含む整理結果を確認し、必要に応じて編集・承認する。
8. 「伝える・今は保留する・伝えない」を本人が選ぶ。
   選択理由は任意で入力できる。
9. 保存する場合は、保存対象を確認し、保存に同意する。
   保存せずに終了することもできる。
10. 保存したメモを、後から本人だけが一覧・詳細で確認・削除できる。

### 中断・失敗時の方針

- 未承認・保存同意なしの内容を自動保存しない。
- 未保存内容の復元を目的として、会話本文をDB・Redis・ログへ保存しない。
- 保存失敗を保存成功として表示しない。
- ブラウザー再読み込み後の相談復帰はMVPでは保証しない。相談の一時状態を取得できず継続できない場合は、内容や内部情報を表示せず、汎用メッセージで案内してUI-002（ホーム）へ戻す。詳細は第8章「一時情報」に従う。
- 利用回数は相談開始時に計上し、同じ相談内で扱い方を選び直しても追加計上しない。
- メモ保存の再試行時は、本人の同じ相談に対する保存済みメモがあれば、新しい行を作らず既存結果を返す。
- AI・サーバー側の失敗、安全案内での終了、一時状態消失時に利用回数を取り消す条件は、後続の利用回数制限Issueで決定する。

### 相談フローの詳細方針

以下はIssue #2・PR #20で決定し、developへマージされた共通前提に基づく。

- 相談テーマは5種類と「その他」とし、名称・説明例はPR #20の決定内容を参照する。
- 感情候補は8種類とし、最も近いものを一つ選ぶ。
- 感情の具体化では、自分の言葉で入力するか、
  「うまく言葉にできない」を選ぶ。
- AIの追加質問は最大3問とする。
- 対話途中の訂正・再確認は追加質問と別枠とし、
  出来事を整理する工程全体で最大2回とする。
- 「訂正入力 → AIが修正後の理解を提示 → ユーザーが再確認」までを1回と数える。
- 訂正・再確認の最大2回は暫定値とし、画面試用・実装結果により見直す。
- 「もう少し整理したい」は、追加質問が3問未満かつ訂正上限に達していない場合のみ選択できる。
- 訂正上限に達した後は追加質問・訂正のやり取りを増やさず、UI-006Bで本人が要約を直接編集する。
- 訂正上限に達した後に追加質問（ask_more）や訂正（correct）を要求された場合は、API側でも409で拒否する。

### 相談テーマ・感情候補

相談テーマは次の「5テーマ＋その他」（選択肢は合計6件）とする。

- 会話・連絡・愛情表現
- 暮らし・家事・生活習慣
- お金の感覚の違い
- 気遣い・思いやりの伝わり方
- 将来・価値観・二人の関係
- その他

感情候補は次の8種類とし、最も近いものを一つ選ぶ。

- 寂しい
- 悲しい
- 不安
- 怒り・いら立ち
- モヤモヤ・違和感
- 傷ついた
- 自分を責める気持ち（情けなさ・罪悪感）
- その他・まだよく分からない

### 決済・プランの扱い

- スクールMUSTである決済機能と、具体的な課金方式を区別する。
- 本Issueでは、最小テスト決済と結果反映をMUST対応範囲として整理する。
- 実際の請求は行わない。
- 月額300円、相談回数、保存件数などの旧版の仮値は、
  正式な仕様として引き継がない。
- 買い切り型・サブスク型の選択は未確定とする。
- 継続課金・Webhook・解約は、採用する課金方式と
  必要な状態反映の確実性に応じて追加要件を定める。
- 決済記録と利用権限は区別する。
  二重通知・再試行・同時操作で権限を重複反映しない。
- 有料権限が終了した場合の既存メモの閲覧・削除・新規保存の扱いは要確認。
  未確定のままメモを自動削除しない。

### 利用制限の扱い

- 相談回数の上限と、1相談内の質問・訂正回数の上限は分ける。
- 利用回数の上限だけを理由として、開始済みの相談の整理・扱い方の選択を途中で拒否しない方針とする。ただし、安全案内への切り替え、本人の中断、認証失効や一時状態消失時まで継続を保証するものではない。安全案内の停止条件はQ-12、回数の取消条件はQ-08で決定する。
- 正式値の決定前は、実装Issueでテスト用の暫定値を変更可能な設定値・定数として管理する案とする。仮値・根拠・適用環境をIssueへ記録し、正式な料金・利用条件として表示しない（Q-08で確認）。
- 利用回数の消費時点、再試行による重複加算、
  同時開始、期間の切り替え方法をAPI設計で定める。
- Redisには本文・入力原文・未承認内容を保存しない。
- Issue #8では、Redis障害時に相談を止めないフェイルオープンを検証した。
  本番で採用する場合は、新規相談と進行中の相談の扱い、
  費用上限、接続タイムアウト、長時間障害時の運用を決める。
- 回数の加算と初回の有効期限設定は、
  途中失敗で期限のないキーを残さないよう原子的に処理する。
  Issue #8ではLuaスクリプトによる方法を確認した。
- TTL方式は採用候補であり、正式な期間とリセット起点は未確定とする。
- 保存件数の上限確認と保存処理は、
  同時操作で上限を超えない方法を設計する。

暗号化した項目の検索・絞り込みを行う場合は、

### AIの安全性

- AIが本人の気持ち、相手の意図、取るべき行動を断定しない。
- AI出力は本人が確認・訂正できる。
- システム側の指示とユーザー入力を明確に分離する。
- AI出力を、そのままSQL・コマンド・外部API操作として実行しない。
- 危機的な内容への応答方針と相談窓口を定める。
- 医療・心理相談の代替や、危機の確実な検出・解決を保証しない。
- 安全上の配慮が必要と判定した場合は、通常の相談整理を継続せず、安全案内を優先する案とする。
- 相談窓口などの重要な案内はAIの自由生成へ任せず、確認済みの固定文言をアプリ側で表示する。
- 危機的内容の検知方法・表示条件・案内文言は、画面・API設計と講師確認後に確定する。

### 鍵管理

- 暗号化方式と鍵の保管・運用は別に設計する。
- 開発・検証・本番で鍵を分ける。
- 鍵へのアクセス権限、更新、紛失、漏えい時の対応を定める。
- バックアップの復元に必要な鍵を、安全に利用できることを確認する。
- 検証で毎回生成する使い捨ての鍵を、本番の継続保存に流用しない。

## 8. データ要件

テーブル定義・型・制約の詳細はIssue #11のDB設計書へ委ねる。
本書では、保存対象と利用者に対する振る舞いを定める。

| データ区分 | 保存・保護方針 |
| --- | --- |
| ユーザー識別情報 | 内部ユーザーIDと外部認証IDの対応など、必要最小限を保存する |
| 利用前注意の表示済み状態 | 初回の詳しい注意と2回目以降の短い注意を切り替えるため、`has_seen_notice`を内部ユーザーに保存する |
| 整理メモ本文 | 本人が承認し、保存に同意した内容だけを暗号化して保存する |
| 整理結果の感情・扱い方・任意の理由 | 本人が保存に同意した整理メモの暗号化対象に含める |
| テーマの選択値・感情カテゴリの選択値 | 整理結果とは別に保存するかは未確定。保存対象の追加は関連設計で確認する |
| メモ管理情報 | メモID・所有者ID・保存日時などを構造化項目として保持する |
| 暗号形式・鍵の識別情報 | 復号・更新に必要な識別情報を保持する。鍵そのものは保存しない |
| プラン・利用権限 | 採用するプランと利用可能な状態・期間を管理する |
| 決済記録 | 本人との対応、外部決済ID、確認済み状態などを必要最小限で保存する |
| 利用回数 | Redisへ本文を含まないカウンターと必要な期間情報を保存する案 |
| 相談中の内容 | 処理に必要な間だけメモリで扱い、永続保存しない |
| カード番号・CVC・認証トークン・秘密鍵 | アプリのDB・Redis・ログへ保存しない |

### 整理メモの保存条件

- 本人による内容の承認と、保存同意を確認する。
- 保存対象を確定してから暗号化する。
- 暗号化や保存に失敗した場合、平文保存へ切り替えない。
- 所有者IDは認証済みユーザーからサーバー側で設定する。
- 再試行による二重保存と、同時保存による件数上限超過を防ぐ。
- 会話原文やAI応答全文を、暗号化していることを理由に保存対象へ追加しない。
- 保存元の相談を識別し、ボタン連打・通信再試行・同時実行で同じ相談から複数のメモを作成しない。
- 保存APIでは認証・ユーザー状態を確認した後、本人の保存済みメモを一時状態より先に確認する。保存成功後に応答が届かなかった場合も、再試行では一時状態が失われていても既存の保存結果を返す。
- 保存済みメモがなく、保存元の一時状態が存在しない・破棄済み・本人所有でない場合は、内容や原因を明かさず404を返し、メモを作成しない。
- 暗号文を別のユーザーやメモの行へ移しても正しいデータとして扱われないよう、暗号文と所有者ID・メモIDを検証可能な形でひも付ける。
- 整理結果の承認（UI-007）と保存同意（UI-009）は別操作とする。承認だけでは永続保存しない。
- 承認済みの整理結果と承認日時は永続化しない一時状態として扱い、保存同意を得たときに保存する。保持方式はAPI設計書を参照する。
- 承認後は整理結果を編集できない。ブラウザーの戻る操作・履歴・直接URLからも編集可能な状態を復元しない。
- 気持ちの扱い方と任意の理由は承認後に入力するため、保存同意の対象として扱う。保存時には承認済みの整理結果を使用し、承認日時と保存同意日時を別々に記録する。

### 一時情報

- 未保存内容の一時保持は、ブラウザーやサーバーの処理中メモリを対象とする。
- 会話本文・未承認内容をlocalStorage、sessionStorage、IndexedDB、
  ファイル、DB、Redisなどへ永続化しない。
- 相談終了・中断・ログアウト等で不要になった内容を破棄する。
- 相談の一時状態を取得できず継続できない場合は、原因や相談内容・内部情報を表示せず、「相談を続けられませんでした。ホームから新しい相談を始めてください」と案内し、UI-002（ホーム）へ戻す。
- 上記のホームへの遷移は相談中の一時状態に関するものであり、保存メモなど別のリソースの取得失敗へ一律に適用しない。
- 保存する・保存せず終了する処理が完了した後は、相談の一時状態を破棄する。保存失敗を保存完了として扱わない。
- 一時状態消失時の利用回数の取り消し条件は、後続の利用回数制限Issueで決定する。404を理由に単純に自動減算しない。
- メモリからの即時完全消去を保証するものではない。
- 一時状態の保持方式・消失条件・ワーカー数・配置条件は、API設計書（PR #27、2fd82dd、第2章）を参照する。運用条件の確認は#49・#50・#64へ引き継ぎ、本書では実装方式を重複定義しない。
- ブラウザー再読み込み後の相談復帰は、APIプロセスに一時状態が残っている場合も含め、MVPでは保証しない。
- 一時状態の保持時間・同時相談数・新規相談開始時の既存相談の扱い・ブラウザー側が相談IDを失った場合の扱いは、#49・#50で取りまとめ、#51・#53との接続を確認する（Q-02）。

### 個別削除・退会

- 本人は自分の保存メモを個別削除できる。
- 決済記録・有料権限がないユーザーについても、本人確認、メモの先行削除、認証アカウント・内部ユーザーの削除、途中失敗後の再実行を確認する。この確認だけで決済連携を含む退会機能全体の完了とはしない。
- テスト決済を持つユーザーの退会条件は#59・#60で整合させる。未完了決済の確認や記録保持の扱いを省略せず、未確定部分はQ-11へ残す。
- 退会開始前に、未完了の決済や継続中の契約など、退会を妨げる状態がないことを確認する。
- 退会処理では対象ユーザーをロックし、`deleting`へ変更する。
- `deleting`中は、退会処理の再実行以外の新規保存・決済・権限付与を拒否する。
- 個人データを早く削除するため、承認済みメモを外部サービスの処理より先に削除する。
- その後、採用する課金方式に必要な処理、Redis利用回数キー、Firebaseユーザー、残りの内部DBデータを順に処理する。
- 各処理は再実行可能にし、途中で失敗した場合は`deleting`の状態から退会処理を再実行する。
- 途中失敗を完了として表示せず、復旧できない場合の運用手順を実装前に定める。
- 決済記録の保持期間と退会時の扱いは、実装前にチームで決める。
- 通常DBでの削除と、バックアップ・外部サービス側の削除を区別する。
- バックアップ復元で削除済みデータが復活することへの対策を定める。

### 検索・一覧表示

- 本人のメモだけを対象とし、取得件数を制限する。
- 暗号化したテーマ・感情・本文を、
  通常のSQLで直接検索できることを前提にしない。
- 簡易絞り込みを追加する場合は、画面要件と暗号化方針を調整する。
- 検索のためにデリケートな内容を平文で複製する場合は、
  保存方針の変更としてチーム確認を行う。

### 共通要件

- 外部サービスの認証情報は適切に管理し、ログやエラーへ出さない。
- 外部サービスの応答を検証してからアプリの状態へ反映する。
- タイムアウト・再試行・重複処理・利用制限を設計する。
- 検証時は、対象・回数・費用見込み・停止条件を事前に記録する。
- 設定した上限を超える検証や有料設定が必要な場合は、事前に確認する。

### OpenRouter

- バックエンド経由で利用し、システム指示とユーザー入力を分離する。
- 構造化出力を受け取る場合も、型・必須項目・長さ・許容値を検証する。
- 利用者に、外部AIへ内容を送信することを事前に説明する。
- OpenRouterとモデル提供者の保持・学習方針、
  スクール提供キーで利用できる設定を確認する。
- アプリ側で会話を保存しないことをもって、
  「外部AI提供者にも一切保持されない」と説明しない。

### Firebase Authentication

- バックエンドでIDトークンを検証し、検証済みUIDを内部ユーザーへ対応付ける。
- トークン内のUIDと、リクエストで申告された所有者IDを混同しない。
- API設計（PR #27、2fd82dd、§3.2）では、内部ユーザーの新規作成経路である`POST /users/me`のみ`check_revoked=True`とする。通常APIでは署名・有効期限を検証し、対応する内部ユーザーがなければ作成せず401を返す。
- 同一UIDの旧トークンによる退会後の内部ユーザー再作成を防ぐ。失効・無効化の即時検知をすべてのAPIで保証する仕様とはせず、認証・退会の実装と結合で適用範囲を確認する（#47・#60）。
- メール確認・パスワード再設定・認証アカウント削除の範囲を確認する。

### Stripe

- テストモードを使用し、実際の請求を発生させない。
- 決済画面への遷移や戻り先の表示だけで、支払い完了を判断しない。
- 本人の決済であることと、購入対象・金額・通貨・支払い状態を
  サーバー側で確認する。
- 決済確認と利用権限への反映に、再試行・同時実行への対策を設ける。
- ブラウザーを閉じた場合などの状態反映方法を決める。
- Webhookを採用する場合は、署名検証・重複・遅延への対応を設計する。
- 継続課金を採用する場合は、更新失敗・解約・返金・権限終了の要件を追加する。
- Issue #6では、買い切り型のテスト決済について、
  支払い成功時だけメモリ上のテストユーザーをfreeからpremiumへ変更できることを確認した。
  この状態はサーバー再起動で失われる検証用のものであり、
  本番の利用権限やDB永続化が完成したことを意味しない。
- キャンセル・支払い失敗・無効なセッションでは、
  有料状態へ変更しないことを確認した。
- 現在の検証構成には、認証済みユーザーとの紐付けがない。
  本実装では、決済セッション・認証済みユーザー・利用権限の対応を
  サーバー側で検証する。
- Webhookを使用しない構成では、
  決済成功後に利用者が戻り先へ到達しなかった場合、
  アプリが支払いを検知できない可能性がある。
- 返金時の状態反映、二重決済防止、DBへの永続化、
  Webhook・解約の要否は、採用する課金方式に応じて決定する。

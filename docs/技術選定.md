## 1. 選定方針

### 前提条件（満たせない候補は除外する）

- スクールのMUST要件を満たせること（フロントエンド／バックエンド分離、コンテナを使った開発環境、RedisまたはMemcachedの利用、決済機能の組み込み、開発用・本番用ログの切り替え、XSS・SQLインジェクション・認可漏れへの対策、バックエンド中心の単体テスト、テスト設計書・テストシナリオ）
- 1ヶ月・5人体制で実装からテストまで行えること
- 企画案8章の保存と安全性の方針を実現できること（会話全文・入力原文・未承認の内容を自社DB・Redis・ログへ保存しない、承認済みメモの暗号化、所有者確認）
- スクール提供のAPIキー（OpenRouter経由）と、スクールで利用可能なモデルを使うこと

### 優先順位

1. 1ヶ月で中心機能とテストまで完成できること
2. デリケートな情報を安全に扱えること
3. チームで分担・レビューしやすいこと
4. チームの習熟度があり、学習コストが期間内に収まること
5. 運用コストを抑えられること
6. 処理速度や将来の拡張性

### 判断の考え方

- 前提条件を満たさない候補は除外し、残った候補を優先順位に沿って比較する。
- 技術検証で動作を確認できたものを優先し、資料だけで比較したものは「保留」または「代替案」として残す。
- 検証で問題が出た場合は、技術を追加して複雑にするより、機能を削って中心価値（相談・整理・選択・承認済みメモ保存）を優先する。

## 3. 比較サマリ

### 3.1 共通構成（フロントエンド・バックエンド・DB・Redis・コンテナ）

**検証結果（#3）**

- `docker compose up --build` で、frontend／backend／db／redisの4サービスがすべて起動した（db・redisはhealthy）。
- Next.jsからFastAPIを呼び出して固定データを表示でき、`/health/db`・`/health/redis` でPostgreSQL・Redisとの疎通を確認した。
- macOS（Apple Silicon、Python 3.14.6）とWindows（Python 3.13.14）の両方で、READMEの手順だけで再現できた。
- #6ではNext.jsの本番ビルド（`npm run build`）も成功している。

**判断**

| 技術 | 判定 | 理由 |
| --- | --- | --- |
| Next.js / TypeScript | 採用 | 起動・連携・ビルドを確認。型によってAPIの項目違いを開発中に見つけやすい |
| React + Vite | 不採用 | Next.jsで問題が出ておらず、切り替える理由がない |
| FastAPI / Python | 採用 | #3〜#8すべてで使用。Pydanticでの入出力検証がAIの構造化出力と合う |
| Django、Node.js（Express／NestJS） | 不採用 | 全検証がFastAPI前提で、変更すると検証をやり直す必要がある |
| PostgreSQL | 採用 | 疎通と暗号文の保存を確認 |
| Docker Compose | 採用 | 5人の環境差（macOS／Windows）を吸収できた |

**MVPへの影響**

- 責務分担は「Next.jsはUIと画面状態、FastAPIは認証・認可・AI連携・保存・暗号化・決済」とする。Next.jsのサーバー機能に業務処理を置かない。
- Python 3.14の環境では、asyncpgを0.31.0以上にする（0.29.0は3.14用のwheelがなくビルドに失敗する）。

### 3.2 SQL実装・ORM

- #3と#7は、asyncpgで直接SQLを書く形で実装しており、SQLAlchemyはどの検証でも使っていない。
- SQLインジェクション対策（MUST要件）として、次を方式に関係なく確定する。
  - パラメータ化クエリ（asyncpgの `$1` 等、SQLAlchemyのバインド変数）を必ず使う。
  - 文字列の連結でSQLを組み立てることを禁止し、コードレビューのチェック項目に入れる。
- ORMを使うか（SQLAlchemy＋マイグレーションツールのAlembic）、asyncpgで直接SQLを書くかは **保留** とし、DB設計（#11）と同じ時期に決める。

| 観点 | SQLAlchemy | asyncpgで直接SQL |
| --- | --- | --- |
| 検証状況 | 未検証 | #3・#7で動作確認済み |
| SQLインジェクション対策 | 標準でパラメータ化される | パラメータ化を各自が守る必要がある |
| マイグレーション | Alembicで管理できる | 別途方法を決める必要がある |
| 学習コスト | 新たに学ぶ必要がある | SQLを書ければすぐ使える |

### 3.3 Redis（利用回数制限）

**検証結果（#8）**

- キー `usage_limit:{user_id}`、値は整数カウントのみ。会話本文や個人情報を保存しないことを実データで確認した。
- 回数の加算（INCR）と有効期限の設定（EXPIRE）を、Luaスクリプトで1回の操作にまとめた。途中で処理が止まっても、期限のないキーが残らない。
- 2人のテストユーザーでカウントが混ざらないこと、上限前・上限到達・上限超過の判定を確認した（仮値：上限3回・TTL60秒）。
- Redisに障害が起きたとき、相談を止めずに処理を続けられること（フェイルオープン）を確認した。

**判断**

| 項目 | 判定 | 内容 |
| --- | --- | --- |
| Redisでの利用回数制限 | 採用 | キー設計とLuaでの原子的な操作を本実装でも使う |
| リセット方式 | 採用（TTL方式） | 日付キー方式・バッチ方式と比較し、最もシンプルなTTL方式を第一候補とする。ユーザーごとにリセットの起点がずれることは許容する |
| 障害時の方針 | 採用（フェイルオープン） | 企画案の「開始した相談は途中で止めない」方針と一致する |
| Memcached | 不採用 | Redisで要件を満たせた |
| 本番の上限回数・期間・TTL・接続タイムアウト | 保留 | プラン仕様（価格・相談回数）の決定後に決める |

**MVPへの影響**

- 利用回数の判定は相談を開始するときだけ行い、開始した相談は途中で止めない（企画案10章）。
- 上限回数は固定値にせず、設定値として扱う（MVP決定記録No.8）。
- 検証では架空のユーザーIDを使ったため、本実装では認証のUID（内部ユーザーID）と紐付ける。

### 3.4 AI連携・AIモデル

**前提**：スクールでOpenRouter経由で利用できるテキスト生成モデルは、たたき台の5モデルから変更なし（2026-09-25確認）。

**検証結果（#4）**

- 5モデルすべてで、OpenRouter経由の接続とJSONの取得を確認した（一次確認）。
- 料金の差と提供元の違いから、DeepSeek V4 Flash 0731とgpt-oss-120bの2モデルを選び、架空の相談例3種（通常2・危機1）で詳細に比較した。
- 11件すべてが、jsonschemaでのローカル検証でSchemaに準拠していた（`validate_schema.py`）。ただし、Schema準拠と内容の品質は別に評価する必要がある。
- 危機例では、最初から安全対応用のSchema（`PororiSafetyGuidanceResult`）を渡して実行した。そのため、通常の相談の流れの中でモデルが危機的な入力を自動で見分けられるか（危機の自動検知）は検証していない。

| モデル | 詳細比較 | 通常例 | 危機例 |
| --- | --- | --- | --- |
| gpt-oss-120b | あり | 概ね良好。ただし、本音が相手側の事情の推測やアドバイス文になる、背景に推測を補う、感情が想定とずれる（「怒り・いら立ち」を想定した例で「不安」）点があった | 通常の整理を続けたと返し（`continued_normal_structuring: true`）、相談先の案内が不足していた |

| GLM 4.7 Flash／GPT-5 Nano／Gemma 4 26B A4B | なし（一次確認のみ） | ― | ― |

たたき台で候補に挙げていたAuthlib・Auth0は、次の理由で今回の比較対象から外した。

- Authlib：OAuth・OpenID Connectを実装するためのライブラリで、ユーザー登録・パスワード管理などは自分たちで作る必要があり、自前JWTと同じく実装量が大きい。
- Auth0：Firebase Authenticationと同じ外部の認証サービスで役割が重なる。Firebaseで要件を満たせたため、別の外部サービスを追加で検証する必要がないと判断した。

**判断**

| 技術 | 判定 | 理由 |
| --- | --- | --- |
| Firebase Authentication | 採用（条件付き） | 唯一、実接続で検証でき、認証・認可ともに期待どおり動作した。チームに利用経験があり、アプリ側でパスワードの保管・照合を実装せずに済む |
| fastapi-users | 保留（代替案） | 未検証のため不採用とはせず、Firebaseで問題が出た場合の切り替え先として残す。ただしメンテナンスモードのため、切り替える場合は保守状況をあらためて確認する |
| 自前JWT | 不採用 | 実装・テスト量が大きく、セキュリティ不具合のリスクが高い（たたき台4章のリスク） |

**採用の条件（本実装までに対応）**

- 失効したトークンや、無効化・退会したユーザーを拒否できることを確認する（検証は `check_revoked=False` で、失効は未確認）。`check_revoked=True` にするだけでは退会後の拒否は保証されないため、アプリ内ユーザーの状態確認とFirebase側の確認をどう組み合わせるかを決めて検証する（#5のREADME）。
- サービスアカウント鍵の扱いを決める。
  - SDKの初期化で認証情報を読み込むため、鍵を渡さないと `DefaultCredentialsError` になった（鍵を使わない構成は未確立）。
  - Firebaseが自動で作る管理用サービスアカウント（強い権限を持つ）の鍵は使わず、専用のサービスアカウントを作る。
  - トークンの署名検証だけなら、IAMロールを付けないサービスアカウントで足りる見込み。一方、`check_revoked=True`（ユーザー情報の参照）や退会時のFirebaseユーザー削除には権限が必要になる。
  - そのため、MVPで必要な操作を洗い出し、それに必要な最小限の権限だけを付ける方針とする（権限の具体的な内容は本実装で検証する）。
  - #5のREADME「本実装で決める事項」でも、トークン検証専用のIAMロールなしサービスアカウント案と、ユーザー削除・失効確認に必要な権限を分けて確認する方針が記載されている。
- Next.jsの画面からFirebaseにログイン・ログアウトし、トークンを更新する流れを確認する（検証スクリプトはREST APIでログインしていた）。
- メールアドレスの確認・パスワード再設定の扱い、初回ログイン時の内部ユーザー作成、退会時のFirebaseユーザーとアプリDBの削除処理を、API・DB設計で決める（#5のREADME）。

**MVPへの影響**

- 内部ユーザーは `firebase_uid`（NOT NULL・UNIQUE）でFirebaseのUIDと対応付ける。
- クライアントが送ってきたUIDや `user_id` は信用せず、必ずトークンから取り出したUIDを使う。
- 認可テスト案（#5のREADME）を本実装のテストに使う：他人のメモの削除は404で実際には削除されない、一覧に他人のメモが含まれない、リクエストの `user_id` を無視する、退会後のトークンでアクセスできない、拒否時にDBが変更されない。
- 保存後のメモは閲覧・削除のみで、更新APIは作らない（MVP決定記録No.7）。

### 3.6 暗号化・鍵管理・非保存設計

**検証結果（#7）**

- cryptographyのFernetで暗号化・復号し、承認済みかつ保存に同意したメモの暗号文だけをPostgreSQLへ保存できた。
- 改ざんされた暗号文や、異なる鍵での復号は拒否された。
- 未承認・保存同意なし・不正な入力・鍵の設定不備の場合は保存されなかった。入力エラー時は固定メッセージを返し、送った本文をレスポンスに含めない。
- テーブルに平文を保存する列がないことを、テストで確認した。
- API処理後のRedisが空であること、レスポンスとPythonログに本文・鍵が含まれないことを確認した。加えて、確認担当（みほ）がPR #22のレビュー時に、DB・Redis・テストのコンテナログを検索し、架空メモの本文と暗号文が含まれないことを手動で確認した。ただし、#7のREADMEにあるとおり、コンテナログ全体と生成した鍵との自動照合は未実施。
- テスト15 passed。

**判断**

| 項目 | 判定 | 理由 |
| --- | --- | --- |
| cryptography（Fernet）によるアプリ層暗号化 | 採用 | 実績のあるライブラリで、改ざん検知も含めて動作を確認できた。鍵をDBに渡さずに済む |
| pgcrypto（DB層暗号化） | 不採用 | 暗号化・復号のたびにSQLで鍵をDBへ渡すため、DBのログ等に平文や鍵が残るおそれがある。また、DBが漏えいしたときに鍵も一緒に漏れるリスクがある（アプリ層暗号化なら、鍵はアプリ側にあり、DBだけ漏れても復号できない） |
| 開発環境の鍵管理（`.env`、Gitにコミットしない） | 採用 | 全検証で `.env.example` のみをコミットし、秘密情報がリポジトリに含まれないことを確認した |
| 本番の鍵管理（Secret Manager等） | 保留 | ホスティング先が未定のため |
| 鍵の入れ替え（ローテーション） | 保留 | Fernetの `MultiFernet` を候補とする（未検証） |

たたき台では「AES-GCM等」を想定していたが、Fernet（AES-128-CBCとHMAC-SHA256の組み合わせ）に変更した。自作の暗号方式は作らない方針は変わらない。

**MVPへの影響**

- 保存できるもの・保存しないものは、#7のREADMEの保存可否一覧に従う。
- 「会話本文をDB・Redis・ログに残さない」ことは、保存APIの範囲でのみ確認した。AIとの対話で複数ターンの文脈をどう保持するか（たたき台4章のリスク「会話文脈の保持」）は、#3〜#8のどの検証でも扱っておらず、保留のまま残る。

  1. プルリクエストごとに、pytestとLintを自動で実行する（Sprint3開始時）。
  2. Next.jsのビルド（`npm run build`）を追加する（フロントエンドの画面実装が始まった後）。
  3. デプロイの自動化は、ホスティング先が決まった後に検討する（MVPの対象外）。
- 注意点：外部API（OpenRouter・Firebase・Stripe）はCIから呼び出さず、モックでテストする。APIキー等をCIに登録しない構成を基本とする。

### 3.9 監視・ログ

- #5・#7で、Python標準のloggingを使い、INFO以上のログとレスポンスに本文・トークン・鍵が含まれないことを確認した。#5ではuvicornの `--no-access-log` で、アクセスログにトークンが残ることも防いだ。
- 開発用と本番用のログの切り替え（MUST要件）は、どの検証でも扱っていない。ただし、デプロイしない場合は「環境変数を切り替えてログの出力内容が変わることを見せる」形で要件を満たすと、講師から回答を得た（2026-09-26）。

| 項目 | 判定 | 内容 |
| --- | --- | --- |
| Python標準logging | 採用 | 検証で使用しており、本文を出さない運用を確認済み |
| 開発用・本番用ログの切り替え | 採用（方式） | 環境変数（例：`APP_ENV`、`LOG_LEVEL`）で出力レベルと出力項目を切り替える。デプロイしない場合も、環境変数を切り替えてログの出力内容が変わることを見せれば要件を満たす（講師確認済み、2026-09-26）。実装・動作確認はSprint3開始時以降 |
| ログに出さない項目 | 採用（ルール） | 会話本文・入力原文・復号後の内容・トークン・鍵をログやエラー詳細に出さない。コードレビューのチェック項目に入れる |
